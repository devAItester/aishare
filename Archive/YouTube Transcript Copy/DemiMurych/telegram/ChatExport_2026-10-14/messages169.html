function digitPermutation(nums) {
    var groups = new Map;

    for (var i = 0, l = nums.length; i < l; i++) {
        var num = nums[i];

        var n = num;
        var mask = 0;
        var length = 0;

        while (n > 0) {
            var digit = n % 10;
            mask |= (1 << digit);
            n = (n / 10) | 0;
            length++;
        }
        
        var key = (length << 16) | mask;

        var group = groups.get(key);

        !group ? groups.set(key, [num]) : group.push(num);
    }

    return Array.from(groups.values());
}

Чтобы разобраться, следует начать с того, какие именно проблемы пытается решить csrf токен.

При решении задач, связанных с каким либо удаленным доступом к тем или иным функциям нашего приложения, мы используем специальным образом сформированные URL. Например https://example.com/delete/123

Если мы совсем упарываемся в стандарты, то мы не просто используем URL, но еще и используем соответствующий запросу метод: GET PUT PATCH и так далее.

Если взять пример выше, то мы должны были бы его запросить с методом DELETE.

Проблемы начинаются тогда, когда серверная часть, обрабатывая наш запрос, https://example.com/delete/123
должна принять решение - а действительно ли нужно его обработать.

Наиболее типичной схемой, принятия решения, является ситуация, когда полученный запрос ассоциируется с конкретным пользователем - есть ли у него (пользователя) достаточные права, чтобы выполнить этот запрос.

Как серверная часть может связать поступивший запрос, с пользователем?

Наиболее простой способ, это вместе с отправляемым запросом со стороны клиента, отправлять некоторый идентификатор того самого пользователя. Этот идентификатор может быть как параметром самого запроса, так и банальной COOKIE

Серверная часть, получив этот идентификатор, решает для себя о возможности выполнения того самого запроса.

Все работает как следует до тех пор, пока реальный пользователь, с реальным браузером выполняет какие-то действия: пользователь тык в кнопку делете, ушел запрос к серверной части, выполнилось делете чего-то важного.


А теперь что во всем этом может быть плохого.
Для простоты предположим, что наша серверная часть, обрабатывает запрос на delete как обычный GET запрос. Так же для простоты предположим, что идентификатор пользователя, отправляется за счет COOKIES, которые бразуер автоматически добавляет к запросу.

Предположим, что мерзкий мурыч, нашел возможность, в код HTML страницы, в тег img подставлять любой URL.

Мерзкий мурыч отправляет такую страницу пользователю, то есть страницу где есть тег
<img src="https://example.com/delete/123">

пользователь ее открывает. Браузер интерпретирует страницу. Автоматически шлет запрос на delete/123 подставляя COOKIE пользователя. Профит - что-то было удалено. Хотя пользователь этого и не хотел.

Подобного рода атаки, стали настолько распространены, что люди задумались что с этим делать.

И возникло решение: каждый подобный запрос, должен обязательно иметь еще один параметр: CSRF токен.

Который формируется при самой простой реализации по схеме: время создания токена + время протухание токена + url страницы +соль.

На выходе строка из куче крокозяблов, расшифровать которую, можно только зная алгоритм формирования и соль.


Что это дает?
Теперь злой мурыч, уже не может просто так подставить в img URL вида /delete/123321

function digitPermutation(nums) {
    const map = new Map()

    for (let i = 0; i < nums.length; i++) {
        const num = String(nums[i])
        const hashArray = Array.from({ length: 9 }, () => 0)

        for (let j = 0; j < num.length; j++) {
            const char = num.charAt(j)
            hashArray[char]++
        }

        const hash = hashArray.toString()

        if (!map.has(hash)) {
            map.set(hash, [ nums[i] ])
        } else {
            map.get(hash).push(nums[i])
        }
    }

    return Array.from(map.values())
}

This use was subsequently adopted by Sussman and Steele when they defined Scheme in 1975, a lexically scoped variant of Lisp, and became widespread.

Sussman and Abelson also use the term closure in the 1980s with a second, unrelated meaning: the property of an operator that adds data to a data structure to also be able to add nested data structures. This use of the term comes from mathematics use, rather than the prior use in computer science. The authors consider this overlap in terminology to be "unfortunate."

И одновременно ПИПЕЦ для системного программиста.

Генераторы - более высокий уровень абстракции чем add.
