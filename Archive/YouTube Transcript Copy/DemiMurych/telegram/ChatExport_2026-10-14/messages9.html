JS это мультипарадигменный язык. Это, как минимум означает, что на JS мы можем худо бедно писать как в императивной парадигме (в частности ООП) так и в функциональной.

Характеристиками ООП явялется: абстракция, инкапсуляция, полиморфизм. Или иными словами набор некоторых методов, которые выполняют одну и туже работу одним и тем же образом.

new - предоставляет общий, один и тот же способ, урегулировать все типичные запросы ООП.

Безусловно, мы могли бы самостоятельно возвращать из функции, согласно некоторой длогике новый обьект. Но тогда, нам пришлось бы самостоятельно реализовывать и всю прочую логику характерную для типичного ООП.

Например - наследование. В самом упрощенном варианте, в прототип ориентированном ООП наследование - это цепочка тех самых прототипов. Каким образом эта цепочка будет задана или построена?

new дает ответ на этот вопрос - используется property prototype конструктора, в качестве источника для протитпа результирующего обьекта. Как следствие, человек который пишет используя ООП точно знает - что любая часть кода, которая использует для создания обьектов new - будет подчинена общей логике прототипов, которая заложена изначльно в JS.

Это становится чуть более понятным, когда мы вспоминаем, что JS сам по себе не существует. JS это что-то, что куда-то встроено. Например в браузер. Как результат, HOST система (браузер) используя концепцию new может предоставлять Вам интерфейс, который будет общим и для JS и для HOST системы.

Например в браузере есть intersection observer api. Это API которое позволяет отслеживать какие из DOM элементов оказались в области отображения. Вызов этого API происходит как
new IntersectionObserver(callback, options);
что сразу дает возможность программисту точно знать:
что вернется обьект
что это обьект будет иметь какую-то структуру
что прототипом этого обьекта, будет то, что связано с Prototype конструктора
что гарантирует наличие определенных методов
и т.д.

То есть на уровне спецификации, закреплен алгоритм создания обьектов с определенными шагами, который вызывает так и никак иначе. При этом эти шаги, позволяют управлять процессом создания единым общим для всех участников способом. Как программистом, так и HOST системой, которая использует тот же самый порядок создания обьекта через new.

Опять же, эта идея получила и продолжения на уровне появившегося символа @@species
A function valued property that is the constructor function that is used to create derived objects.
Что позволяет решать типичные ооп задачи, еще гибче.

И при этом не иметь никаких гарантий, что все программисты будут реализовывать единый интерфейс такого наследования.

ТОЕСТЬ
Согласно спецификации - каждый блок {} ( а это не просто блок, это любое место где вы пишите фигурные скобки - от функции до if catch и вобоще всего) должно попрождать новую LexicalEnviroment.

Что привело в ужас инженеров RunTime. Когда это появилось, первое что произошло - это просадка производительносмьти ВСЕХ runtime более чем на 30%. Кто помнит эти времена, расскажет как официальная Node рекомендовала не использовать let const.

Когда прошла стадия отрицания - ну типа какой долбоптица это придумал, стали думать как решать эту проблему. Поскольку создание окружений - это ОЧЕНЬ дорого. Что конечно совершенно не известно тем долбоптицам которые думали о спецификации let и const. Как итог в случае V8 эту проблемы решили *супер изящно* -
несмотря на тот факт, что спецификация, требует создания нового окружения, V8 шлет это в пешее эротическоей путешествие, основываясь на том, что это окружение нужно только для отслеживания новых идентификаторов в рамках блока. И решает эту проблему тем способом, что в рамках нового блока, все идентификаторы, получают новые имена в рамках bytecode. То есть приравнивают их поведение почти к Var.

ByteCode V8 - это регистровая виртуальная машина, в которой каждый идентификатор внутри единицы кода ( это функция) обозначен как регистр r с цифрой от 0 до n
 то есть, если внутри функции вы заводите идентификатор - то он в рамках виртуальной машины имеет обознавчение как R0 если это первый идентификатор в функции. Аргументы функции имеют идентифкаторы A0-An

Так вот, встречая блок кода, и в нем конструкции вида let или const, V8 забивает создавать новое окружение, и просто для каждого имени заводит новый регистр. То есть внтури функции условное имя let myVar; получит регистр R0; И если внутри блока опять появится let myVar - то оно получит R с номером какой там будет по счету. Если это единсвенные идентифакторы то это будет R1

() => {
   let myVar = 10;   // Это R0
   {
       let myVar = "dolboptica menya pridumala"; // Это R1
    }
}

PromiseJob - це повноцінне queue в рамках специфікації ECMA.
Саме завдяки йому в EventLoop HTML5 з'являеться те, що зветься microtask queue, яке так саме є повноцінною чергою.
Тобто гарантується виконання усіх елементів в черзі строго так, як вони туді потрапляють.

GenericJob - це список (Set). Він є прототипом Task queue в Event Loop HTML5. Або тому що частіше звуть як Macrotask.
Це не черга. Тобто згідно специфікації ECMA завдання Job які потраплють у цей список можуть бути виконані як завгодно в якому завгодно порядку.
В HTML5 так саме. Але, згідно інших алгоритмів, які використовують Task Queueu слідчить, що черги виконання завдань також притримуються.

Найважливіше це те що:
GenericJob або Task queue вбо Macrotask - це звичаний список того, що потрібно зараз виконати з одним важливим доповненням - коли завершується виконання будь якого Job з цього списку - обов'язково йде перевірка - чи не з'явилося щось у PromiseJob /microtask queu. І якщо з'явилося - то відразу починається виконання цього списку строго по черзі до тих пір коли усі завдання не будуть виконані.
