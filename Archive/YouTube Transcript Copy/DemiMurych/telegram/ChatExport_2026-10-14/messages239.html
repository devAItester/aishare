Метод reject конструктора Promise возвращает результат вызова rejected функции для конструктора, который был обозначен как тот при помощи которого был создан промис.

И это НЕ ОБЯЗАТЕЛЬНО БУДЕТ promise в состоянии rejected

Согласно спецификации, никто не мешает использовать СВОЙ конструктор для создания промиса, который для метода rejected вернет fulfilled promise.

Следует для себя отметить что:
Promise.reject - это не создание Promise в состоянии реджектед.
Это возвращение результата после вызова функции reject у конструктора который обозначен как тот, который привязан к целевому промису.

Ровно тоже самое для Promise.resolve.

Простым и наглядным примером этого может служить вот этот код

при вызове по умолчанию, Promise.reject вы вызываете стандартную реджект функцию конструктора Promise которая и возвращает по умолчанию тот самый реджектед промис,

переопределив которую, вы можете вернуть что угодно.

Promise.reject - єто вызов реджектет функции, но не создание реджектед промиса.

При очень точном совпадении по времени SQLite мог решить, что страницы уже перенесены из WAL в основной файл, хотя этого не происходило. Часть данных исчезала, а база становилась повреждённой.

Баг получил название WAL-Reset. По оценке разработчиков SQLite, он существовал минимум 16 лет и был настолько редким, что для тестов пришлось специально писать код, который провоцирует нужную гонку. Tailscale ловила его чаще из-за агрессивного ручного checkpointing.
