# Принципы архитектуры: анализ материалов Тимура Шемсединова

## Главный вывод

Сложность нужно контролировать на промежуточном уровне: между отдельными функциями/файлами и всей системой. Прежде чем выбирать сложный генератор, базу данных или фреймворк, следует определить модули, границы ответственности, контракты и направление зависимостей.

В материалах Тимура это связано с декомпозицией абстракций, GRASP, SOLID, модульностью, внедрением зависимостей, инверсией управления, разделением ответственности (SoC), контрактным моделированием и слоистой архитектурой.

## Принципы, полезные этому проекту

### 1. Separation of Concerns (SoC) — разделение ответственности

Разделять части, которые меняются по разным причинам. Текст страницы меняется при редактировании знаний; меню — при изменении навигации; CSS — при изменении оформления; общий шаблон — при изменении каркаса документа. Если всё это повторено в каждом HTML-файле, независимые изменения сцеплены между собой.

**Применение:** Markdown-файлы содержат содержание страниц; YAML — список пунктов меню; HTML-шаблон — повторяемую оболочку; CSS — оформление.

### 2. Decomposition / Single Responsibility — декомпозиция и одна ответственность

Разбивать систему не просто на маленькие файлы, а на части с ясными контрактами и самостоятельной причиной для изменения. Избыточная декомпозиция тоже вредна: маленький проект не нуждается в десятках абстракций без реальной нагрузки.

**Применение:** один общий layout отвечает за оболочку страницы; данные навигации — за пункты меню; каждая страница — за одну тему; таблица стилей — за визуальные правила.

### 3. Modularity, cohesion and coupling — модульность, связность и зацепление

Модуль должен иметь высокую внутреннюю связность и минимальные случайные зависимости от других модулей. Физическая папка сама по себе не создаёт модульность: важно, какие данные и решения пересекают границу.

**Применение:** сайт не должен читать файлы из Archive. Перемещение или удаление временного архива не должно ломать сборку, URL, меню или содержимое опубликованного сайта.

### 4. Single Source of Truth и DRY

Один факт или правило следует хранить в одном авторитетном месте, если дублирование не требуется намеренно. DRY — не запрет на повторяющийся текст вообще; он касается повторения знаний и правил, которые потом могут разойтись.

**Применение:** общий header/footer не копируется в каждой странице; пункты меню определены в одном YAML-файле; CSS подключается из одного внешнего файла. Смысловые ссылки остаются явными в самих материалах, пока автоматизация не окупает свою сложность.

### 5. Контракты и декларативное моделирование

Компоненты должны обмениваться понятными данными через стабильные структуры, а не полагаться на скрытые детали друг друга. Схема или контракт задаёт допустимые поля и смысл данных.

**Применение:** навигационная запись имеет два поля — <code>title</code> и <code>url</code>. Страница имеет метаданные front matter: <code>title</code>, <code>description</code>, <code>permalink</code>, <code>layout</code>, <code>section</code>. Это простой контракт, который можно проверить и расширить при необходимости.

### 6. Dependency Inversion / Inversion of Control — инверсия зависимостей и управления

Высокоуровневая логика не должна быть жёстко привязана к конкретному низкоуровневому механизму. Не каждый проект требует DI-контейнера; принцип полезен как направление зависимостей.

**Применение:** содержание не зависит от разметки навигации. Общий шаблон получает пункты меню из данных. Замена или изменение меню не требует редактировать каждую страницу. Для текущего статического сайта достаточно механизма данных Jekyll — отдельный контейнер зависимостей был бы избыточен.

### 7. Information Expert и ясное владение данными

Ответственность следует отдавать той части модели, которая обладает нужными данными. Не создавать параллельный реестр только ради удобства, если он дублирует существующую информацию.

**Применение:** метаданные страницы находятся рядом с содержимым страницы; глобальное меню находится в файле меню; общие стили — в CSS. Карта сайта перечисляет страницы самого сайта, а не все файлы репозитория.

## Что не следует переносить механически

- Repository, DAO, ORM и другие паттерны доступа к данным не нужны только потому, что проект хранит тексты: сейчас нет динамического хранилища или запросов к базе.
- DI-контейнер, микросервисы, клиентский фреймворк и отдельный runtime не решают существующую проблему дублирования шаблонов.
- Автоматическая генерация обратных ссылок пока не обязательна: сначала должны быть ясные исходные связи и стабильные адреса.
- Декомпозиция не означает «как можно больше файлов». Критерии — независимое изменение, понятный контракт и снижение зацепления.

## Вывод для проекта

Сначала разделить содержимое, данные навигации, шаблон и CSS. Затем определить контракты и связи между страницами. Только после этого выбирать автоматизацию для карты сайта, хлебных крошек и обратных ссылок. Генератор должен собирать публикацию из собственных данных сайта, а не использовать временный архив как неявную базу.
