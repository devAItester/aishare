# GitHub: получение содержимого при ошибках curl

Тебе нужно просить меня **использовать GitHub API и доступные инструменты GitHub вместо попытки получить страницу только через `curl`**.

Здесь важно различать три инструмента.

| Инструмент | Что это | Когда использовать |
|---|---|---|
| `curl` | Консольная утилита для HTTP-запросов | Получить HTML страницы или содержимое URL |
| GitHub REST API | Официальный программный интерфейс GitHub | Получить файлы, коммиты, ветки, метаданные репозитория |
| GitHub connector / tools | Инструменты интеграции с GitHub, доступные мне в ChatGPT | Читать файлы репозитория, изучать коммиты и другие данные через доступные операции |

## Какую фразу использовать

> Если не получается получить страницу GitHub через curl, используй GitHub API и все доступные тебе GitHub-инструменты. Найди альтернативный способ получить исходное содержимое, проверь результат и продолжай выполнение задачи. Не останавливайся на сообщении об ошибке curl.

## Что именно я должен делать

1. **Проверить `curl`** — установить, что именно не работает: соединение, HTTP-ответ, URL или доступ к содержимому.
2. **Использовать GitHub connector** — если нужная операция доступна через подключённые инструменты.
3. **Обратиться к GitHub REST API** — например, получить файл через Contents API или изучить коммиты через Commits API.
4. **Попробовать альтернативный URL** — например, `raw.githubusercontent.com` для исходного файла вместо HTML-страницы `github.com`.
5. **Проверить полученные данные** — убедиться, что получено именно нужное содержимое, а не страница ошибки, пустой ответ или устаревшая версия.

## Официальная документация

- [GitHub REST API — Contents](https://docs.github.com/en/rest/repos/contents) — получение содержимого файлов.
- [GitHub REST API — Commits](https://docs.github.com/en/rest/commits/commits) — просмотр коммитов.
- [GitHub REST API — Introduction](https://docs.github.com/en/rest/about-the-rest-api) — устройство API и способы доступа.

**Практическое правило:** не делай вывод об отсутствии доступа из ошибки одного инструмента. Различай прямую проверку сайта и проверку альтернативного источника или артефакта сборки. Не утверждай, что результат проверен, пока действительно его не проверил. Учитывай реальные доступные инструменты: нельзя заранее обещать, что любой из них сработает в каждом случае.
