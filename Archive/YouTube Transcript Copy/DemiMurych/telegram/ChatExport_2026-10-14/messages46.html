Array.prototype.snail = function (rowsCount, colsCount) {
  if (this.length !== rowsCount * colsCount) return [];

  const arr =  new Array(rowsCount)
  .fill()
  .map(() => new Array(colsCount).fill(0));

  let isReverse = false;
  let index = 0;
  
  for (let i = 0; i < colsCount; ++i) {
    if (!isReverse) {
      for (let j = 0; j < rowsCount; ++j) {
        arr[j][i] = this[index++];
      }
    }
    else {
      for (let j = rowsCount - 1; j >= 0; --j) {
        arr[j][i] = this[index++];
      }
    }
    isReverse = !isReverse;
  }

  return arr;
};

Конецптуально ни в чем, особо… Но сделано для людей, а не для чужих )
Начинается все как-обычно:
1. В системе диспачится event
2. Если есть соответсвующий handler (чистая функция), то он запускается,
на вход принимает сам evеnt (данные), и набор коэфектов
коэфект - это, в основном, кикие-то данные, значения которых ты не знаешь
на момент диспача event-a, или хочешь получить данные актуальные
не в момент определенния эвента, а вот именно тогда, когда эвент будет обработан.
Примером коэфекта могут быть: app-стейт, текущее время или данные из local storage.
Тут надо понимать, что в clojure, почти все данные имутабельные,
поэтому, ты не можешь передать ссылку на мутируемый обект
(можешь, на самом деле, но это отдельная структура данных - atom)
Поэтому, коэфект - это рецепт (функция) определенная ранее, которую re-frame вызовет
в тот моммент, когда эти данные понадобятся.
Так вот, получили мы эвент и коэфекты (текущую дату и стейт, к примеру)
В эвент-хендлере у тебя не ссылка на стей, а просто данные стейта, можно рассмативать
ее как имутабельную копию стейта.
Дальше ты что-то делаешь со стейтом, нарпимер обновляешь часы, ты опять получаешь такие-же
новую версию стейта. Возникает вопрос, что дальше, как актуализировать стейт?
Ведь эвент хендлер у нас чистая функция!
Делается это следующим образом:
эвент хендлер возращает набор эффектов, опять-таки в виде данных, то есть:
{db: newDB} - где db - это им эффекта, а newDB - это новая версия нашего стейта.
Можно возвращать много эффектов. Существуют встренные эффекты, такие как db для стейта,
или fx - для диспача какого-то другого события (таким образом, формируя цепочки последовательных или
паралельных событий) ну и пользоватальские, само-собой.
3. Дальше re-frame сам разберется с эффектами )
4. Есть еще подписки, это такие вочеры за определенной частью стейта, если в стейте что-то поменялось,
и есть вочер на этот кусок - он вызовет функцию подписки, которая на вход получит эту самую часть
стейта и вернет что угодно.
Ееще можно делать подписки на подписки 😉 и тогда мы получим не куски стейта, а уже результаты работы
функций подписок. С подписками еще много можно разного делать, но это основное.
5. Используешь подписки, как источники данных для компоненнтов.
Итого: диспач-ивент-> эвент-хендлер -> эффект хендлер -> новый стейт-> обновилась подписка ->
перерендерился компонент.

Но это долеко не все, тут и интерцепторы, и дев-толзы или еще можно всего интересного

В clojure типов данных всего ничего +- как js. В основном ты оперируешь данными, а не типами… а для описания данных в clojure есть такая вещь как spec. Это более мощная конецпция чем типы. Условно, написав спеку на свои данные, ты из коробки получаешь не просто валидацию (возможность узнать, что к тебе пришла строка в функцию, а не число), но коерсинг (если ждешь число, но пришла строка и эту строку можно конвернуть в число, то на выходе получишь число). Правили вилидации и коерсинга могут быть пользовательскими, то есть, ты можешь написать функцию, которая по любым правилам, которые ты сам сможешь придумать будет валидировать твое значение или коерсить. И все это в рантайме. Опять же лучше на примере:
Возмем, какой-нить rest api роут, создание пользователя или все что угодно, что принимает какой-то json, обрабатывает эти данные и возвращает другой json.
Понятное дело, что как-только мы что-то засунили в json, мы тут же потеряли очень много...
с этим форматом данных мы не можем ничего делать, поэтому прегоняем это в мапу (условный js-объект), получаем такой-же аморфный объект, а хотим
получаить дату как дату, а не строку, set как set, а не массив ну и тд... Коерсим наши данные, в случае успеха - получаем гарантировано
валидный объект в рантайме или четкое описание ошибки, где и что не получилось сконвертить... Дальше что-то делаем и теперь нам надо вернуть
ответ пользователю. Если на той строне не clojurescript, то надо данные перегнать в json, при этом, например, мы не хотим что бы чувсвтителные данные,
типа паролей или чего-то такого улетело на клиент. У нас спека на исходящий объект, при помощи которой мы закодируем наши данные в json, и в этой спеке
сказано, что поле пароль, нужно вырезать, номер заменить карты на звоздочки...
Все это мы можешь разменить где-то в мидлварах и не парится этим в прикладном коде.
Спека - это декларативное описание не только струтуры данных но операций трансформации (encoding/decoding) и это касается не только json->object, но и object->object.
То есть, в разных слоях приложения объект может интерпритироваться по разному, таким-образом гибкость, по стравнению с системой типов, просто "безграничная" ))
Остается только решить где это тебе нужно, в основном спеки используются для контрактов между слоями приложений, редко кто пишет спеки на все подряд.\
