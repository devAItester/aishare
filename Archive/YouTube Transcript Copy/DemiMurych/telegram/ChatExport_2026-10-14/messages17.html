Все задачи, которые я публикую и где явным образом не указано иного, касаются ТОЛЬКО JavaScript.
То есть для их решения не требуется никаких сторонних API подобных EventLoop. Только спецификация ECMAScript.

Так делается намеренно,и делается для того, чтобы четко сформировать устойчивый стереотип у программиста: где непосредственно язык JavaScript: а где что-то иное (внешнее API)



Такие вещи как Promise закреплены в спецификации как функционал, который может функционировать БЕЗ чего-либо подобного EventLoop. То есть закреплены как самостоятельный самодостаточный функционал.

При этом, важно так же отметить, что несмотря на то, что с академической точки зрения, Promise это крайне полезная штука в программировании, в самом JavaScript их используют в первую очередь как интерфейс между асинхронным внешним API и самим агентом выполняющим код JS.


То есть, важно понимать две вещи:
Promise работают без любого внешнего API
Promise - удобны в JS в первую очередь там, где присутствует вызов любого внешнего API, которое не может вернуть результат своей работы синхронно.
Например console - внешнее api которое прекрасно справляется со своей работой синхронно. А вот fetch нет.


А теперь все что касается async function и await.
async/await это синтаксический сахар поверх логики генераторов с промисами на перевес.
Как следствие, работа async/await ровно так же, как и Promise или генераторы - не требует ничего извне - в том числе и Event Loop.

Но при этом, для большинства программистов связанных с браузером, не существует ничего другого в их коде, кроме как связывание внешнего API через тот же EventLoop посредством спецификации Promise. Или использования async await.

Что происходит только потому, что они (программисты или задачи которые они решают) пока слабо доросли до нормального программирования, как и инструменты которые они используют подобные React Vue Angular и т.д.

Каждый RunTime реализует свои собственные алгоритмы построения AST.
Поскольку, в случае синтаксиса JS, это одна из очень энергоемких задач, то колличество и качество разных оптимизаций от RunTime к RunTime может сильно меняться. Как следствие и то, что называют AST в самом RunTime так же.

По большому счету AST - это сленг описывающий привычную схему разбора синтаксиса.
Строго говоря RunTime вообще не обязан его строить, а может реализовать любой другой эффективный алгоритм.

Потому, единственная рекомендация - это использование флага вывода на stdOut AST дерева для каждого конкретного RunTime. У V8 это --print-ast
