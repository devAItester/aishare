Это храктерно для любого скриптового языка.
Строго говоря, в любом скриптовом языке ( питон не исключение) интерпретация каждой комманды происходит именно в момент выполнения. При этом все что написано в строке - как то вычисляется.
Как? - Описано в спецификации. Каждая часть выражения описана как алгоритм вычисления.

По этой причине когда мы в JS видим строку:
1;
это не единица. Это выражение которое языком интерпретируется и приводит к тому, что это выражение возвращает ссылку на HEAP где описан обьект, который собой хараткеризует единицу.

Так во ВСЕХ интерпретируемых языках

Отличия начинаются там - где вступает в дело оптимизирующий алгоритм. Который патается привести подобный интерпретируемый код к виду, который бы выполнялся максимально быстро.
(Мы же понимаем что можно сойти сума, если каждое число описывать как обьект в куче)

В V8 например, подобная (1) будет преобразована в набор инструкций, кроторые посторяются избежать создания полнойенного обьекта в HEAP.
Но подчеркну - это попытки компилятора сделать код быстрее. А не то, что JS работает как то иначе.

Проффесиональный программист на языке JS старается код писать так, чтобы оптимизирующий компилятор мог выжать из этого максимум.


Фраза Дональда Кнута про - преждевремнную оптимизацию как корень всех зол - именно про это.
То есть про необходимость программисту научиться писать код так, чтобы компилятор МОГ сделать все необходимое для оптимизации кода.

А не про то - что пишите код как вам вздумается, а потом когда нибудь оптимизируейте его когда для этого возникнет необходимость

Declarative Env record - это описание общей структуры окружений, которой ползьуются другие части спецификации.
А именно: object env record, variable end record, lexical env record, private env record, function env record и так далее.

Это база для построения логики работы окружений. При этом каждое окружение имеет свои специфические ососбенности, которые описаны отдельно в спецификации. Например variable env record, которая как не турдно догадаться обслуживает идентификаторы созданные благодаря var statement работает инчает чем lexical enviroment record, которая обслуживает работу идентификаторов созданных при помощи let и const.
При этом Lexical Env Record может в отдельных случаях выступать общим источником и для идентификтаоров заявленых при помощи var и при помощи const и let.


Но и это не главное. Главное то, что когда говорят про Лексическое окружение - то есть про Lexical Environment - то говорят о некоторой сущности наделенной определенными качествами, в рамках привычного жаргона - про области видимости. НО этих качеств в полном обьеме в JS нет. И что еще хуже в JS есть концепция Environment - оркужений, которая по своему звучанию крайне похожа на Lexical Environment из жаргона о областях видимости. Чем сбивает людей с толку еще больше. То есть слово и там и там одинаковое, а суть разная.

Environment в JS работают ВООБЩЕ НЕ ТАК, как это используется в рмаках жаргона о областях видимости вцелом и Lexical Environmetn в частности. Слово коуржение ( Environment ) которое используется и там и там, по разному интеропретируется как в случае жаргона, так и в случае спецификации языка.

Тут треба поділити на те що було до того як з'явился let та const. І після цього.

До let/const все було просто - оточення, створювалось навколо функції і тільки неї.
Глобальне оточення - це теж саме. Тобто потрібно лише уявити, що код у глобальному оточенні, виконується так само як і код у функції.

Це оточення - має в собі де кілька інших під-оточень. Знати зараз про які - не має необхідності. Досить того, що усі вони виконують одне й теж саме завдання.

З того часу, коли з'явилися let так const почалася "маячня". Бо з цього моменту, кожний блок коду (тобто код який виглядає як:
{
// [тут якісь код]
}
став призводити до того, що у оточенні, яке було створено для функції, змінюється лише одне під оточення, яке зветься як Lexical Declaration Environment. На кожний випадок, коли ми зустрічаємо блок {}

Точно розбиратися в тому, де та яке оточення кого подменило - не варто. Це важливе лише для тих, хто працює з новими частинами специфікації. Для звичайного програміста JS достатньо розуміти те, що кожній блок коду створює своє оточення, при цьому оточення саме функції - має біль розширені опціїї, які щодо ідентифікаторів ніяк не торкаються.

Можно було б сказати, що й оточення функції це теж саме що і у блоку. Але це не зовсім так, бо це торкається інших частин мови. Хоча, щодо саме ідентифікаторів, то не буде помилки вважати, що кожна функція, та кожний блок, створюють оточення, які працюють однаково.

Тобто, якщо уявити стару версію оточень, яка була лише для var, де кежне оточення було суто прев'язане до функції, то зараз, можливо казати, що все теж саме, але прив'язано до блоку, де функція - один з блоків. Але треба пом'ятати, що це спрощене правила стосуються лише ідентифікаторів.

Обобщенный набор рекомендаций по работе с Exotic Object Array
#array #opti #perf #tips

1] Если Ваш Array имеет фиксированный размер, и при этом его элементы не будут изменяться - смело используйте литеральную форму определения такого обьекта. Например:
var theArr = [1, 2, 3];

2] Если элементы будущего Array будут изменяться, то рекомендуется использовать либо констурктор Array либо его функциональную форму:
var theArr = new Array (1, 2, 3);
theArr[0]=7;
таким образом вы избежите ненужной нагрузки на GC, поскольку Ваш Array сразу будет создан из предположения что элементы будет изменяться. Или способ из бонус 2 в конце поста.

3] Если Ваш Array может расти в размерах, относительно его начальной формы - то настоятельно рекомендуется об этом позаботиться заранее. То есть инициализировать Array таким образом, чтобы V8 заранее предоставил достаточное колличество слотов для новых элементов. Потому как мы помним, что подобныя операция стоит очень дорого. Тем дороже чем больше наш Array.

4] Настоятельно рекомендуется не делать дырок в Array
var theArr = [1, 2, 3];
theArr[7]=1;
приведет к созданию дырок для элементов с индексами 3,4,5,6. Обработка подобных Array в среднем на 30% медленее чем аналогичных и без дырок.

5] Настоятельно рекомендуется в Array держать элементы одного и того же типа:
1. Целые числа в пределе от -1073741824 до 1073741823
2. Любые прочие числа
3. Все прочие типы данных

6] Не забываем что V8 устроен таким образом, что изменив модель представления Array на худшую, к лучшей уже вернуться нельзя. Только пересоздавать Array.

7] Помним что Array по задумке V8 инженеров, предназначен для обработки данных в условиях, когда для одних и тех же данных многократно повторяются одни и теже операции. Для подобных ситуаций внутри V8 и созданы все оптимизации, которые опираются на описание выше.

8] Памятке по аллокации слотов:
var theArr = []; // 0 слотов.

var theArr = Array(); // 4 слота

var theArr = new Array(); // 4 слота

var theArr = Array(10); // Аллокация 10 слотов. Тип HOLEY_SMI_ELEMENTS

var theArr = Array(1,2,3,4,5); // Аллокация 5 слотов под пять элемента БЕЗ COW

var theArr = [1,2,3, 4, 5]; // Аллокация 5 слотов под пять элемента и статус COW
theArr[0]=1; // Копирование 5 элементов в новую область и снятие статуса COW

theArr.push(1); // 6 + 3 + 16 = аллокация 25 слотов, высокая вероятность копирования всех элементов в новую память. Тип PACKED_SMI_ELEMENTS неизменен.

Язык Си, это универсальный язык программирования, который позволяет решать задачи любой сложности, код которого компилируется в архитектуро-зависимое представление. То есть программа на языке Си, при компиляции преобразовывается в набор процессорных команд ( которые проще всего смотреть в их интерпретации на языке ассемблера)

Из этого следует, что в первую очередь, программист на языке Си, использует возможности той архитектуры, под которую потом будет собираться программа. Строго говоря, хорошим программистом на языке Си можно быть только тогда, когда ты точно знаешь от того как работает процессор, до того как работает та операционная система которую ты используешь.

Например на языке Си пишут в том числе и оперционные системы.


Язык JavaScript - это интерпретируемый язык, который никак не привязан к архитектуре, кроме той, которая описана его спецификацией. Программа на языке JavaScript может выполняться в любом месте и в любое время, если в этом месте и времени, существует интерпретатор который может выполнить программу.

А теперь следите за руками
Язык Си - архитектурно зависимый. Это язык, который в первую очередь используется для системного программирования. А системное программирование, это всегда такой код, который напрямую зависит от той архитектуры в которой он исполняется.

То есть программист на языке Си, старается по максимому использовать все возможности архитектуры, для того, чтобы его код был максимально эффективен. Да. Асболютно все в JS єто обьекты.
Нет никаких исключений на уровне самой спецификации.

Исключения возникают только тогда, когда RunTime пытается оптимизировать код.
При этом, важное значение имеет тот факт, когда именно код оптимизируется - на уровне простого байт кода, или на уровне его максимального с точки зрения производительности представления - то есть на уровне машшиного кода.


В случае если мы говорим про ситуацию, когда большая часть нашего кода, никогда не познает любви от TurboFan, то есть никогда не будет приведена к машинному представлению - то в этом случае мы должны всегда думать о любых типахз как о обьектах. И ответ на Ваш вопрос простой - всегда все обьект.

В случае если мы говорим про ту часть кода, которая познала любовь TurboFan, то есть код выполнялся натсолько часто, что RunTime возлюбил его и передал в турбоФан, в этом случае такие штуки как: undefined, null, true, false имеют свои константы на уровне втнуртреннего представления. И проверки на то, состоит ли значение скажем в true, представлет из себя следующий ассемболерный код:

cmpq [rNN+0xNN],rdx; // сравнить с числовой константой
jz 0xNN; // если да перейти


То есть важно понимать, что:
На уровне внтуреннего представления, такие вещи как undefined, true. false, null - это обьекты.
При этом на уровне байткода, выделены специальные команды, которые заточены на то, чтобы проверить конректное занчение. Например в v8 есть команда testUndefined

И на уровене машинного кода, это приобретает еще более простой вид, где конректное значение проверяется на константу, которая предопредеена на моенет старта runTime

Что это значит с практической точки зрения:
Это значит, что JS код может себе позволить без значимых проблем производительности, иметь идентификаторы, которые проверяются на undefined и/или null/true/false при условии, что тип данных который будет связан с идентификатором вне этих типов, всегда останется одним и тем же.

То есть, если в функцию передается параметр, который может быть undefined, а может быть числом - то это приемлемо. В идеале, чтобы был всегда числом.
Но если заходит идентификатор, который может быть undefined а может быть числом или строкой - то это катастрофа. С которой RunTime пытается бороться создавая два разных представления функции - для строки и для числа. И это уже называется полиморфным представлением кода и это уже отдельный разговор.

Сталкиваясь с JS, в том случае если мы хотим понимать как все работает, должны помнить 3 вещи:
1) Есть спецификация, которая описывает все множество возможностей языка, предоставляя примеры алгоритмов реализации той или иной возможности. При этом спецификация не накладывает на реализацию спецификации (TunTime) обязательств делать именно так, как описано в примере алгоритма, но обязует RunTime делать так чтобы при одних и тех же входящих данных на выходе было одно и тоже.

Например: В спецификации описан алгоритм метода sort для Exotic Object Array, при этом, эффективность этого алгоритма сомнительна. При этом спецификация не накладывает обязательств на то, чтобы алгоритм был именно такой, но накладывает обязательства на то, чтобы результат был тот же самый, а приведенный алгоритм является примером, позволяющим сравнить полученный результат с эталонным. По этой причине во всех RunTime sort реализован иначе чем в спецификации, но выдает теже результаты.

2. Спецификация, определяет типи данных, которые имеют исключительное поведение - они должны при получении их значения, возвращать некое Primitive Value отвечающее значению спецификации. То есть, RunTime - должен сам для себя решить задачу, а что для него является undefined? а чем для него является null?

В рамках V8 это решается путем использования простого обьекта типа oddball_type, который создан для того, чтобы описывать поведение таких простыхз констант как undefined null true false и т.д


3. Потому, ответ на вопрос в следущем - являются ли undefined и null обьектами в рамках спецификации? Нет не являются.
Могут ли быть undefined и null в рамках их реализации RunTime не обьектами или не какойто-то логической структурой подчиненной какому-то правилу, позволяющему понять где null а где undefined? Ответ так же нет.

Вот и выходит, что на уровне практической реализации undefined и null это обьекты. Максимально простые - но обьекты.
Почему это не просто какие то константы типа 0000h - это false, а 0001H это true, а 0003h- это undefined?

По простой причине - с точки зрения производительности, намнго эффективнее отдать значения по умолчанию под числа - то есть под то представление которое естественно для процессоров всех текущих архзитекутр. Потому как чаще всего они оперируют именно ими.

А когда требуется разобраться с какойто вирутальной сущностью, типа null или undefined, или false или true - то жффективнее представить их в виде простого обьекта.

ИЛИ ограничить набор принимаемых по умолчанию чисел.
Например в 32 битной архитектуре максимальное целое это чуть больше 4 млрд: 4294967295
или в бинарном виде: 0b11111111111111111111111111111111

Для того, чтобы определить константу, например для undefined, нам нужно от этого набора битов отрезать как минимум один бит, чтобы выделить его под определдение константы и тогда наши 4 млрд уже становятся 2 миллиардами. 2147483647

А мы всего лишь, взяли только одну констунту. А нам надо взять еще минимум 4.

Очевидно что в этой истории, любой системный программист, выделит константы в подобие максимально простого обьекта, который будет обозначать одним обзим способом. Что и делает V8 и прочие рантайм.
