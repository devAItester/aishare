🔸 1. Термины и определения
1.1 Property - элемент объекта, связывающий property key с множеством property attributes.
1.2 Own property - свойство объекта, содержащееся в нём непосредственно.
1.3 Inherited property - own property или inherited property прототипа объекта.
1.4 Prototype - объект, предоставляющий общие свойства для других объектов.
1.5 Internal Method - алгоритм спецификации, описывающий семантику объекта.


🔸 2. Internal Method [[getPrototypeOf]]
Сигнатура: ( ) → Object | Null
Описание:
Determine the object that provides inherited properties for this object. A null value indicates that there are no inherited properties.

Определите объект, который предоставляет унаследованные свойства для этого объекта. Значение null указывает на отсутствие inherited properties.



🔸 3. Мой код
var object = {
    property: undefined,
};
var object_prototype = {};
Object.setPrototypeOf(object_prototype, null);
Object.setPrototypeOf(object, obj_prototype);
console.log(Object.getPrototypeOf(object));

Функции setPrototypeOf и getPrototypeOf у объекта Object в точности соответствуют функциям build-in объекта Object спецификации, соответственно. В следствие этого в консоль выведется {}, то есть object_prototype.


♦️ 4. Проблема
Данное 1: Объект object не содержит ни одного inherited property.

Данное 2: Cогласно описанию internal method getPrototypeOf: Значение null указывает на отсутствие inherited properties.

Следствие: [[getPrototypeOf]] должен вернуть значение null, а не объект.

❗️Из всего выше написанного можно сделать вывод, что описание Internal Method [[getPrototypeOf]] неверно.

Ниже — краткий чеклист проблем и исправлений для вашего кода; сначала самое вероятное решение, затем дополнительные проверки.
Главное (скорее всего причина)

Atomics.wait/notify работают только на Int32Array. Вы создаёте header как Int32Array — ок, но при вызове Atomics.notify/Atomics.wait вы передаёте туда тот же объект header и индекс 0, — это правильно. Основная проблема: в write вы используете Atomics.wait(header, 0, Atomics.load(header, 0)); — это неправильно, потому что значение, передаваемое в wait, может измениться до вызова и вы тем самым ждёте нефиксированное значение; лучше ждать ожидаемого фиксированного состояния 2 (или 1→0). Также Atomics.wait блокирует поток (в worker это ок), но в main thread нельзя блокировать — в браузерном main-потоке Atomics.wait блокирует UI и не разрешён в некоторых окружениях; вы в read используете waitAsync, а в write — синхронный wait: если write выполняется в main thread и read в worker, или наоборот — возможен дедлок. Решение: использовать waitAsync в обоих сторонах или синхронный wait только в воркерах. Обычно писатели (workers) должны блокировать синхронно, а главный поток читать через waitAsync.

Исправленный поведение-зачин (рекомендация):

При ожидании освобождения буфера в write: while (Atomics.load(header, 0) !== 0) { await (Atomics as any).waitAsync(header, 0, Atomics.load(header, 0)).value; } — то есть использовать waitAsync и ожидать конкретного текущего значения (потому что waitAsync берёт snapshot value). Или лучше: loop читаем status; если status !== 0 — ждём, передавая snapshot status.
Не делать Atomics.wait(header, 0, Atomics.load(header, 0)); синхронный wait с динамическим третьим аргументом может привести к моменту гонки.

Конкретные правки (минимально):

let cur = Atomics.load(header, 0); while (cur !== 0) { Atomics.wait(header, 0, cur); cur = Atomics.load(header, 0); }

В read вы используете waitAsync(header, 0, status).value — это хорошо. После прочтения вы делаете Atomics.store(header,0,0) и Atomics.notify(header,0) — ок.

Вся штука в том, что
когда мы пишем
function doThing( i = 1 ) {

Параметры функции - это выражение которое исполняется в момент выова.

Код вида
i = 1

внутри параметров - это выражение которое должно быть выполнено.

strict или non strict?

Ведь функция может быть вызвана из разного кода.


В силу этого, на уровне static sematics наложено ограничение, что
ЕСЛИ используются выражения внутри параметров функции, ТО нельзя переопределять режим STRICT внутри самой функции, ТАК КАК само выражение, будет исполнено в контексте ВЫЗОВА функции, которое не обязательно будет STRICT.
