# Сначала данные, потом представление.

Структура должна оставаться понятной в текстовом редакторе, терминале и на GitHub. Генератор помогает собрать публикацию, но не должен быть единственным местом, где устройство системы имеет смысл.

Материалы сайта находятся в `pages/`: главная страница лежит в корне этого каталога, а тематические страницы — в папках разделов и подразделов. Физические пути организуют исходники; `permalink` в front matter отдельно определяет публичный URL. Поэтому реорганизация каталогов не должна сама по себе менять адреса страниц.

## Разделение ответственности

| Слой | Где хранится | За что отвечает |
|---|---|---|
| Содержимое страниц | `pages/`, сгруппированный по разделам и подразделам | Текст и метаданные конкретной страницы |
| Иерархия меню | Путь внутри `pages/` | Раздел и уровень вложенности страницы в меню |
| Подпись пункта меню | Front matter: `nav_title`, с запасным вариантом `title` | Человекочитаемое имя в навигации |
| Публичный адрес | Front matter: `permalink` | Стабильный URL страницы, независимо от физического пути |
| Порядок соседних пунктов | Отдельное явное правило, ещё предстоит реализовать | Предсказуемый порядок страниц на одном уровне |
| Общий шаблон | `_layouts/default.html` | Общая HTML-оболочка и отображение меню |
| Оформление | `assets/main.css` | Визуальные правила |
| Сборка | Jekyll / GitHub Pages | Преобразование Markdown в HTML |
| Исходный архив | `Archive/` | Исторические материалы; не является зависимостью сайта |

## Что здесь от Jekyll, что от Oscean, а что от нас

Это три разные вещи, и их важно не смешивать.

**Jekyll — механизм сборки.** Он преобразует Markdown, использует YAML-данные и Liquid-шаблоны, а на выходе создаёт статические HTML-файлы. После сборки браузер получает обычные HTML, CSS и ссылки.

**Oscean Дэвида — исследуемый референс.** У него изучаются визуальный язык, организация страниц, многоуровневая навигация, смысловые связи и поведение интерфейса. Мы не переносим реализацию Oscean на Uxntal: воспроизводим нужные свойства в собственной реализации на Jekyll. Текущая версия ещё не является точной копией оригинала; простое меню — предварительная реализация, а не доказанное воспроизведение меню Дэвида. См. [визуальный язык и проверку соответствия](styling.html).

**Наши архитектурные решения** — декомпозиция, разделение ответственности, уменьшение связности и дублирования, явные зависимости и минимально достаточная сложность. Это принципы проектирования, применённые к задаче, а не свойства самого Jekyll или Oscean. Они согласуются с [материалами HowProgrammingWorks о принципах проектирования](https://github.com/HowProgrammingWorks/Principles).

## Пример модели меню

Путь `pages/music/classical/mozart.md` задаёт положение страницы внутри `Music → Classical`. Front matter может отдельно содержать `title: Wolfgang Amadeus Mozart`, `nav_title: Mozart` и `permalink: /mozart.html`. Таким образом, полное название страницы, короткая подпись меню и URL не обязаны совпадать. Это иллюстративный пример модели, а не существующий файл.

## Поток сборки

```text
Markdown + front matter + HTML/Liquid + CSS
                    |
                  Jekyll
                    |
            статические HTML-файлы
                    |
         браузер: HTML + CSS + ссылки
```

## Почему не хранить всё в HTML

Когда каждая страница вручную содержит одинаковые меню, заголовки, метаданные и подвал, изменение общего элемента требует редактировать много файлов. Это дублирование создаёт риск расхождений. Общий шаблон хранит повторяемую структуру один раз, а страницы — только собственное содержимое и метаданные.

## Данные и отношения

Содержимое не должно зависеть от оформления. Иерархия меню должна выводиться из пути страницы, подписи — из front matter, а публичные адреса — из `permalink`. Общий шаблон отвечает за представление. Эти значения нельзя смешивать: перемещение файла не должно незаметно менять публичный URL, а изменение подписи меню не должно требовать переименования файла.

Пока не нужна отдельная база данных или JavaScript-приложение: Markdown, YAML, Liquid и статическая сборка покрывают текущие требования. Сложность добавляется только при появлении задачи, которую более простая структура не решает.

## Граница архива

`Archive/` — соседняя коллекция в репозитории, а не каталог сайта. Она исключена из публикации, не включена в меню, не является источником данных для сборки и может быть перемещена или удалена в будущем без изменения модели страниц. Сайт имеет собственное содержимое и собственную навигацию.
