Ще раз.
Алгоритм щодо Number.isNaN (number):
1. If number is not a Number, return false.
2. If number is NaN, return true.
3. Otherwise, return false.


Перший крок - переірка на тип для даних - чи є це Number.
Якщо ні - то повертажться false.

Другий крок, використовується конструкт If number is NaN
Згідно специфікації, конструкт "is" це перевірка згідно алгортиму SameValue

Який виклядає ось так: SameValue ( x, y )
1. If SameType(x, y) is false, return false.
2. If x is a Number, then
   a. Return Number::sameValue(x, y).
3. Return SameValueNonNumber(x, y).

тобто у SameValue передается якесь value для порівняння з NaN.
У першому кроці алгоритму SameType(x, y) ми відразу повертаємо false у випадку коли value не є Number. Бо тип у NaN це саме Number.

Замість IGOGO:
В алгоритмі Number.isNaN перший крок нічого не верішує.
Тобто якщо ми його видалимо за алгоритму - то нічого не змінеться. Не існує такої ситуації коли б, перша перевірка чимось відрязналясь від тієї яка відбувається на другому кроці.

Тобто, якщо переписати алгоритм щодо Number.isNaN до виду

2. If number is NaN, return true.
3. Otherwise, return false.

Все буде працювати так само.

Що і викликало питання - чого ми можемо не розуміти, щодо того чому інсує перший крок який нічого не вирішує.

Разница тут не в «математике», а в том, как движок JIT-компилятор (например, V8) преобразует JavaScript-код в байткод (а потом и в машинный код).

1. Что происходит в a + 10

Движок видит: «слева переменная, справа литерал-число».

Это часто используемый паттерн → можно сразу сгенерировать простую инструкцию: взять a, прибавить число 10.

В байткоде это может превратиться в что-то вроде:

LoadVariable a
AddSmi 10
Return


(где Smi — small integer в V8).

2. Что происходит в 10 + a

Движок видит: «слева литерал, справа переменная».

По стандарту JS оператор + — не только арифметика, а ещё и конкатенация строк.

Чтобы не нарушить спецификацию, движок обязан проверять:
а) что слева число (ок, это литерал 10),
б) что справа тоже число (или сделать ToPrimitive, если это объект, строка и т. д.).

И хотя оптимизатор может потом выкинуть лишние проверки, на первом шаге генерации байткода там появляется чуть больше инструкций: загрузка литерала, проверка типа правого операнда, возможно приведение.

3. Почему именно «на 2 строки байткода»

Это как раз те самые лишние проверки/приведения для универсальности (сначала берём 10, потом a, потом проверяем a, а уже потом складываем).
Когда a + 10, движок может сразу сделать оптимизированный путь «переменная + smi».
