# Rules

## Проверка изменений и публикации

После любого изменения сайта или шаблонов не завершать работу на проверке исходного кода или успешной сборки.

1. Дождаться завершения соответствующего GitHub Actions workflow. Не писать «сборка ещё выполняется» и не передавать проверку пользователю, пока можно дождаться результата.
2. Убедиться, что сборка и deployment завершились успешно именно для коммита с последними изменениями.
3. После публикации проверить исходный HTML реально опубликованной страницы, а не только Markdown, Liquid-шаблон или HTML из локальной сборки. Проверить несколько страниц, если изменён общий шаблон.
4. Сверить опубликованный HTML с ожидаемой структурой и ссылками. Если задача касается отображения или взаимодействия, дополнительно проверить поведение в браузере. При обнаружении регрессии, например пропавшего меню, проверить не только наличие соответствующей разметки, но и необходимые CSS, JavaScript, пути ресурсов и фактическое поведение.
5. Если выбранный способ проверки не сработал, не останавливаться на сообщении об ограничении и не перекладывать задачу на пользователя. Установить вероятную причину сбоя проверки и попробовать подходящий альтернативный способ, инструмент или сервис: например, другой HTTP-клиент, GitHub Pages / Actions deployment status, опубликованный URL, GitHub API или браузерную проверку. Выбирать альтернативу по причине сбоя и критерию проверки, а не формально перебирать инструменты.
6. Продолжать диагностику и проверку, пока не получено достаточное подтверждение результата либо не исчерпаны разумные альтернативы. Только после этого, если проверка всё ещё невозможна, точно описать, какие способы использованы, что удалось установить, какая часть результата остаётся непроверенной и почему. Не утверждать, что исправление проверено, если это не подтверждено опубликованным результатом.
7. Если проверка показывает регрессию, исправить её и повторить цикл: commit → дождаться build/deploy → проверить опубликованный HTML → проверить поведение. Не останавливаться на предположении, что изменение должно работать.

**Критерий готовности:** исправление подтверждено на опубликованном результате. Успешная сборка — необходимое, но недостаточное условие; неудача одного способа проверки означает необходимость диагностики и поиска альтернативы, а не завершение работы.
