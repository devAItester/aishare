FLAT-FILE TEXT DATABASES

Цель
  Сначала воспроизвести простой файловый и текстовый подход XXIIVV / David.
  Не придумывать поверх него собственную модель базы данных. Улучшения добавим
  только после того, как станет понятно, что именно в исходном подходе работает.

Отправная точка
  У Давида это прежде всего filesystem + text + маленькие инструменты.

  Unix:
    "Write programs that do one thing and do it well."
    "Write programs to work together."
    "Write programs to handle text streams, because that is a universal interface."

  Поэтому здесь:
    каталог = место, в которое можно перейти
    файл = текст, который можно прочитать или изменить
    путь = адрес
    ls / cd = навигация
    cat = чтение
    grep = поиск
    tree = обзор дерева

  Это не означает:
    каталог = уровень классификации
  Такая интерпретация пока не является частью эксперимента.

Модель Давида, которую воспроизводим
  1. Файловая система уже является структурой.
  2. Каталоги дают адрес и последовательное движение по дереву.
  3. Файлы содержат обычный текст.
  4. Небольшие программы работают с этим текстом.
  5. Один инструмент не обязан знать всю систему.

  В M/PC это сведено почти к примитивам:
    dir = показать файлы текущего места
    mov = перейти в путь и снова показать содержимое
    txt = прочитать текстовый файл начиная со строки
    get = получить содержимое файла

  Наша первая версия на обычном Linux должна сохранить именно эту простоту,
  используя стандартные shell-инструменты вместо отдельного файлового менеджера
  или СУБД.

Структура эксперимента
  flat-file-text-databases/
    01-it/
      02-dev/
        03-linux/
          04-arch/
            05-niri/
              shortcuts.txt

  Здесь пять уровней вложенности нужны для эксперимента с навигацией.
  Числа в именах — техническая метка глубины, а не утверждение о классификации.

Как работать
  Перейди в корень:
    cd ~/aishare/flat-file-text-databases

  Посмотри текущее место:
    pwd
    ls

  Перейди на один уровень:
    cd 01-it

  Вернись:
    cd ..

  Посмотри дерево:
    tree

  Если tree не установлен:
    find . -type d | sort

  Дойди до файла:
    cd 01-it/02-dev/03-linux/04-arch/05-niri

  Прочитай:
    cat shortcuts.txt

  Для длинного текста:
    less shortcuts.txt

  Найди текст во всей базе:
    grep -Rni 'ssh' .

  Найди только txt:
    grep -Rni --include='*.txt' 'ssh' .

  Найди файл по имени:
    find . -type f -name '*.txt' | sort

Навигационная идея
  Не строим отдельный индекс и не вводим собственный DB-язык.

  Базовый цикл:
    ls
    cd name
    ls
    cd name
    cat file.txt

  Если известно слово, не нужно знать адрес:
    grep -Rni 'слово' .

  Если известен файл:
    find . -name 'file.txt'

  То есть есть два естественных способа движения:
    по дереву = cd / ls
    по содержимому = grep

Формат текста
  Файл должен оставаться читаемым обычным cat.

  Отступы разрешено использовать как визуальную структуру:
    тема
      раздел
        пункт
          подробность

  Но это пока соглашение текста, а не схема базы данных.

  Не требуется:
    JSON
    YAML
    SQL
    Markdown
    обязательный набор полей

  Если для конкретной записи удобен формат "дата + текст", можно использовать
  его напрямую. У Давида, например, календарь хранит события в обычном текстовом
  файле: дата, tab, название события.

Практический принцип
  Сначала выбираем самое простое представление, которое уже поддерживается
  файловой системой и Unix-инструментами.

  Не добавляем:
    индекс
    отдельный DB-формат
    приложение для навигации
    обязательную мета-схему

  пока не появится конкретная проблема, которую они решают.

Что проверяем экспериментом
  1. Насколько быстро можно найти нужную тему через cd/ls.
  2. Насколько быстро можно найти её через grep.
  3. Удобнее ли читать несколько маленьких txt или один большой.
  4. Помогают ли отступы внутри файлов.
  5. Нужен ли вообще отдельный индекс.
  6. Где файловая система перестаёт быть удобной.
