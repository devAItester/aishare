# SQLite: служебные события Telegram

## Файлы

- `membership-history.sqlite3` — готовая SQLite-база.
- `membership-history.sqlite3.sql` — полный SQL-импорт, из которого базу можно пересоздать.
- `build-membership-database.py` — безопасная сборка базы из SQL-файла с проверкой целостности и количества строк.

## Источник и охват

Источник: Telegram Desktop export `ChatExport_2026-10-14`, каталог с 252 HTML-страницами `messages.html` … `messages252.html`.

Экспорт сообщений охватывает период с 2023-05-10 по 2026-10-14. Извлечено 4 498 системных сообщений со всех 252 страниц; на 194 страницах есть системные сообщения, на 58 — нет. В таблице `source_pages` сохранено покрытие каждой страницы и число извлечённых записей; сумма этих чисел равна 4 498.

Это база **системных сообщений**, а не копия всего текста переписки.

## Состав данных

| Тип | Количество |
|---|---:|
| `invite` — приглашение участника | 4 481 |
| `pin` — закрепление сообщения | 4 |
| `group_title` — изменение названия | 4 |
| `group_conversion` — преобразование группы в супергруппу | 1 |
| `group_photo` — изменение фотографии | 1 |
| `service_other` — прочие системные события | 7 |
| **Всего** | **4 498** |

В этой выгрузке не обнаружены явные системные записи о вступлении, самостоятельном выходе, удалении или бане участника. Это не доказывает, что таких действий не было: экспорт Telegram Desktop не является полным журналом членства.

Запись `X invited Y` фиксирует приглашение, но сама по себе не доказывает, что приглашённый вступил или что численность группы изменилась на единицу. Не использовать количество приглашений как количество вступивших.

## Схема

### `service_events`

- `event_id` — локальный последовательный ключ SQLite.
- `source_page` — номер HTML-страницы экспорта.
- `telegram_message_id` — ID системного сообщения Telegram.
- `date_hint` — дата из ближайшего предшествующего разделителя даты в HTML, формат `YYYY-MM-DD`.
- `event_type` — классификация системного сообщения.
- `timestamp_utc` — оставлен `NULL`: точное время системных сообщений в HTML-экспорте отсутствует.
- `actor_or_subject` — имя из текста события, если его удалось выделить без догадки; это не Telegram user ID.
- `raw_text` — исходный текст системного сообщения после декодирования HTML-сущностей.

**Важно:** `date_hint` — точность до дня, а не точное время события и не UTC timestamp. Не сортировать такие записи как будто у них есть точное время внутри дня.

### `source_pages`

Одна строка на каждую из 252 страниц: имя файла и число извлечённых системных сообщений. Нулевые страницы тоже сохранены.

### `export_metadata`

Параметры источника, охват и контрольные количества.

## Быстрый доступ

Открыть базу:

```sh
sqlite3 membership-history.sqlite3
```

Число записей по типам:

```sql
SELECT event_type, COUNT(*) AS events
FROM service_events
GROUP BY event_type
ORDER BY events DESC;
```

Приглашения по дням (ISO-даты сортируются хронологически):

```sql
SELECT date_hint, COUNT(*) AS invitations
FROM service_events
WHERE event_type = 'invite'
GROUP BY date_hint
ORDER BY date_hint;
```

Все приглашения за 2024 год:

```sql
SELECT date_hint, telegram_message_id, source_page, actor_or_subject, raw_text
FROM service_events
WHERE event_type = 'invite'
  AND date_hint >= '2024-01-01'
  AND date_hint <  '2025-01-01'
ORDER BY date_hint, event_id;
```

Проверка покрытия страниц:

```sql
SELECT COUNT(*) AS pages,
       SUM(service_event_count) AS extracted_events,
       SUM(CASE WHEN service_event_count = 0 THEN 1 ELSE 0 END) AS empty_pages
FROM source_pages;
```

Проверка целостности SQLite:

```sql
PRAGMA integrity_check;
```

В базе 4 498 событий — для такого объёма обычные выборки выполняются быстро без дополнительных индексов. При существенном росте набора можно добавить индексы по `date_hint`, `event_type` и `telegram_message_id`.

## Пересборка

Python 3, только стандартная библиотека:

```sh
python3 build-membership-database.py
```

Проверить уже существующий файл через SQLite engine в режиме read-only, без изменения базы:

```sh
python3 build-membership-database.py --check
```

Скрипт откажется перезаписывать существующую базу. Для явной пересборки:

При пересборке скрипт сначала создаёт временный файл, выполняет SQL-импорт, проверяет `PRAGMA integrity_check`, число событий и покрытие страниц, закрывает соединение и только после успешной проверки атомарно заменяет целевой файл. Режим `--check` открывает существующую базу только для чтения.

## Граница применимости

Эта база полезна для исследования приглашений и других системных событий в экспорте. Она не заменяет Admin Log, Telegram Statistics или отдельные измерения member_count. Для восстановления динамики численности нужны источники, которые фиксируют фактические вступления/выходы и дают корректную временную привязку.
